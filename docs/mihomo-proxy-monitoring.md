# Mihomo 原节点检测与故障邮件

本功能配合根目录的 `mihomo-fallback.production.yaml` 使用。Mihomo 负责选择备用节点；sub2api 负责检测、展示和邮件通知。不会自动修改账户绑定或代理管理状态。

## 上线顺序

1. 将完整 Mihomo 配置写入现有 ACK Secret，并自行重启对应 Pod。五个美国业务入口保持原端口，每组优先使用自己的原节点。
2. 发布包含本次前后端代码的版本。后端启动时自动应用 `251_proxy_test_tasks.sql`，增加代理检测配置和两张定时任务表。
3. 在「IP 管理」编辑对应的本地代理，在「Mihomo 原节点检测」中选择「Mihomo（单独检测原节点）」，填写与 Mihomo 配置一致的原节点名称、原节点 SOCKS 检测端口和 fallback 组名，保存后点击「测试连接」。已有代理的三个配置值会保留，无需重新填写。
4. 在系统设置中配置并验证 SMTP，再在 IP 管理页打开「定时检测任务」，勾选需要检测的代理，填写邮箱、Cron 和时区后启用。

| 原节点 | HTTP 业务端口 | SOCKS 业务端口 | 原节点检测端口 | fallback 组 |
|---|---:|---:|---:|---|
| us1 | 7893 | 7903 | 17903 | us1-fallback |
| us2 | 7895 | 7905 | 17905 | us2-fallback |
| us3 | 7896 | 7906 | 17906 | us3-fallback |
| us4 | 7897 | 7907 | 17907 | us4-fallback |
| us5 | 7898 | 7908 | 17908 | us5-fallback |

上表是现有生产配置的对应关系，不是程序允许的节点清单。原节点名称、检测端口和 fallback 组名均可在页面填写，新增 `us6`、`us7` 或其他名称的节点无需修改 sub2api 源码。

业务代理地址必须为 loopback，sub2api 和 Mihomo 必须共享同一个 Pod 网络。启用 Mihomo 原节点检测时，三个字段必须一起填写：原节点名称与组名去除首尾空白后不能为空，各最多 100 个 UTF-8 字节；检测端口必须是 1～65535 的整数，且不能等于业务端口。名称可以包含中文和内部空格，不要求使用 `usN` 或 `-fallback` 格式，但必须与 Mihomo 中的名称完全一致，包括大小写。检测请求固定使用 `socks5h://127.0.0.1:<检测端口>`，账户继续使用上方配置的业务代理地址和端口。切换为普通代理并保存，可清除三个检测配置字段。

页面填写的是该业务代理记录的检测元数据，不需要在 IP 管理中额外创建一条检测端口的代理记录。sub2api 不会自动创建或修改 Mihomo 监听器与代理组，字段通过保存校验也不能证明 Mihomo 配置正确：检测监听器必须固定指向原节点，业务监听器必须指向 fallback 组；组类型必须是 `fallback`，首个成员必须是填写的原节点。保存后需要测试并确认三列状态。

## 新增节点示例

以下以新增 `us6` 为例。`7899`、`7909`、`17909` 是未被占用时可以采用的端口示例，实际以你的 Mihomo 配置为准；增加节点无需新增数据库字段或修改 sub2api 代码。

1. 在 Mihomo 的 `proxies` 中增加真实的 `us6` 节点参数。若继续使用现有香港中转链路，保留 `dialer-proxy: hk1`。
2. 在 `proxy-groups` 中增加独立的 `us6-fallback` 组，首个成员为 `us6`，后面按顺序填写其他美国备用节点。例如 `proxies: [us6, us1, us2, us3, us4, us5]`，健康检查可沿用现有组配置。
3. 增加 HTTP 业务监听器 `7899 → us6-fallback`、SOCKS 业务监听器 `7909 → us6-fallback`，以及固定原节点的检测监听器 `127.0.0.1:17909 → us6`。检测监听器必须是 SOCKS 类型，且不能接到 fallback 组。
4. 若希望原来五个组也能使用 us6 作为备用，将 us6 加入相应组的备用列表，保持各组自己的原节点仍是首个成员。五个现有业务入口及其检测端口无需改变。
5. 校验并更新 Mihomo 配置，由管理员重启或重新加载 Mihomo，使新增监听器和代理组生效。
6. 在 IP 管理新增或编辑 SOCKS 业务代理 `127.0.0.1:7909`，启用 Mihomo 原节点检测，填写下表三项并保存，然后点击「测试连接」。不要把业务端口改成 `17909`。
7. 将该业务代理加入所需的定时检测任务。Mihomo 配置的变更不会自动将新代理加入任务。

| 页面检测字段 | 示例值 |
|---|---|
| 原节点名称 | `us6` |
| 原节点检测端口 | `17909` |
| fallback 组名 | `us6-fallback` |

后续新增 us7 时重复上述操作即可，例如使用尚未占用的 SOCKS 业务端口 `7910`、检测端口 `17910`，填写原节点 `us7`、组名 `us7-fallback`，并确保 Mihomo 配置中存在相应组和监听器。端口和命名没有递增规则要求，由管理员配置。

如果 us6 只作为现有五组中的备用成员，没有独立业务入口或独立原节点检测需求，只需新增 Mihomo 节点并加入相应组；原有业务代理在切换后可以显示 `us6（备用）`，无需在 IP 管理额外建一条记录。

## 三列状态

- **原节点状态**：通过页面填写的检测端口固定检测原节点，绕过 fallback；仍保留 Mihomo 中该节点配置的中转链路。现有五个节点使用上表的 `1790x` 端口，新节点可以使用其他未占用端口。
- **当前新连接出口**：同一检测轮读取本 Pod 的 Mihomo 控制器 `127.0.0.1:9090`。它表示检测时的新连接首选节点；已有 TCP、HTTP/2、SSE、WebSocket 连接可能仍使用原连接。
- **业务入口状态**：通过账户使用的业务端口建立新连接，允许 Mihomo 选择备用。

原节点失效、备用正常时，显示「故障 / us2（备用） / 可用」，测试连接的 `success` 仍为 false。控制器不可达只影响出口列。结果超过 1 小时显示过期；每行提供检测时间和执行实例。

Mihomo 配置代理使用独立连接执行 `HEAD https://cp.cloudflare.com/generate_204`，严格要求 204，不跟随重定向，正常校验 TLS。质量检查同样使用原节点；质量结果独立于三列连通性状态。

「地理位置」来自原节点的出口信息。原节点连通性检查成功后，通过同一个固定原节点 SOCKS 检测端口查询 IP、国家和城市，并与业务入口检测并行执行，查询超时不超过单次网络探测超时。位置查询失败、超时或只返回 IP 时，国家/城市可能留空，不影响节点健康、业务入口状态及故障告警；新检测不会沿用旧位置，也不会用备用节点的位置代替原节点。

## 定时任务与邮件规则

建议使用五段 Cron `*/5 * * * *`、时区 `Asia/Shanghai`、连续失败阈值 1、每次网络探测超时 10 秒。每个任务支持 1～20 个代理、1～10 个收件人，阈值为 1～20，超时为 3～30 秒。同一代理只能加入一个启用的任务。启用时还会检查代理数量、单次超时和收件人数量的组合是否能纳入 5 分钟运行预算；过大的组合需要拆分任务或减少超时、收件人。

只有定时执行更新正式告警周期。原节点连续失败达到阈值后，按收件人汇总故障节点发信；持续故障不重复通知已成功接收的人。SMTP 失败在下个检测周期、节点仍故障时重试。定时检测确认恢复后清除周期，下次故障可再次通知。配置错误、内部取消等未知状态不会当成节点故障发信。

「立即执行」及代理行手动测试刷新检测结果，不累计或清除正式告警周期。「发送测试邮件」是显式独立操作，也不改变正式周期。启用任务前必须有 SMTP 配置；任务停用不影响 Mihomo fallback。

任务和通知进度持久化到 PostgreSQL。执行、任务编辑、代理配置修改共用会话级 advisory lock，多 Pod 时只由拿锁的实例检测其本地 sidecar。每轮整体最多运行 5 分钟，网络请求、SMTP 和取消清理均有时间上限。重启后只补一轮到期任务。

## 验收

1. 五个原节点都正常时，确认五组各自优先原节点。
2. 在隔离环境让 us1 的真实链路失败，保留 us2 正常。确认原节点故障、业务入口可用、首选为备用；仅关闭 `17903` 不能验证业务切换。
3. 等待定时检测，确认邮件包含原节点故障、同轮业务状态、组首选、执行实例与时间；持续故障只通知一次。手动测试不发送正式告警。
4. 模拟一个收件人发送失败，确认下轮只重试失败收件人。恢复原节点并经定时检测确认，再次失效应重新告警。
5. 修改原节点配置或在检测中重启服务，确认旧检测不能覆盖新配置，通知周期正确恢复。
6. 新增一个未内置的节点（例如 us6 或中文名称节点），配置独立 fallback 组与检测监听器，确认无需改代码即可保存、测试、显示三列状态并加入定时任务。编辑后重新打开，确认三个字段保持原值；切回普通代理并保存，确认三个字段清空。
7. 检查填写不完整、端口超出范围、检测端口与业务端口相同等情况会拒绝保存。另在隔离环境故意填写一个不存在或首成员不匹配的 fallback 组，确认出口列显示异常且不会误报已确定的当前出口；按正确配置修复后重新测试。

探测成功只表示指定检测目标可达，不能证明 GPT 账号认证、额度或 OpenAI 访问正常。邮件直接通过 SMTP 尽力发送；SMTP 已接受但持久化前进程退出时，下一轮可能重复通知。管理员收到故障邮件后自行维护代理并重启服务。
